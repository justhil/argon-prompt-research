Epistemic Rigor & Causality Audit · 事实与推论的严格边界

我们在 104 场实验中直接观测到了什么？什么属于不应武断下结论的边界？

为确保技术报告的严谨性，我们将“可由实验日志 100% 证实的观测事实”、“从思维链原文直接提取的因果链路”与“受控实验变量边界”明确区分如下。

Evidence-Grounded Analysis
1. 100% 直接观测证实的实证事实 (Observed Facts)

工具调用序列与代码残留的硬性统计

  • 空白桩 vs 半成品的显著分水岭：当待修函数为空桩（throw new Error("TODO")）时，无护栏对照组也会主动调用 read_file；但当入口文件已有 15~30 行代码且包含一处显眼的表面浅层 Bug（如漏写 return、* 1000 乘除写反、漏清空 input.value = ''）时，C0 在 k=3 的 24 场中有 21 场（87.5%）在 Turn 1 零次调用 read_file 直接调用 edit_file。
  • 通用口号（T-Gen）完全无效：在第一批 32 场实验中，加入 "IMPORTANT: Do not hallucinate. Be accurate and careful" 后，通过率仍为 4/8 (50.0%)，残留幻觉符号数反而达到 24 处（高于原版 C0 的 21 处）。
  • 第 4 档护栏组（T-Tier4）的零方差表现：在第一批（8/8 场）与第二批 k=3（24/24 场）共 32 场独立会话中，达成 100% 目标依赖文件先读后改（合计 70/70 文件次）、100% 隐藏 Oracle 通过、0 处幻觉符号残留。
2. 从 Thinking 思维链原文直接提取的机制 (Direct Trace Evidence)

为什么模型不觉得自己在“编造幻觉”？

  • 浅层归因满足（Surface-Bug Satisficing）：检查盲改场次的 reasoning_content 可见，模型在看到表面 Bug 后会直接写下 "The bug is clear from the code... I'll use edit_file to fix it"。一旦找到一个能合理解释报错的浅层原因，模型便立即停止向底层模块深挖。
  • 调用处上下文盲信（Implicit Call-Site Trust）：当入口文件里已经写着 message.notifyLimit(...)（Delulu D1），或者同一文件上方出现了合法的 Result.ok(...)（自建 T2）时，模型在思维链中将其视作“当前仓库已存在的既有事实”，因此哪怕收到 "Do not hallucinate" 的警告，它也认为保留 notifyLimit 或补写对称的 Result.err 是顺理成章的。
  • 旁路冒烟测试麻痹：运行默认 npm test 看到仅覆盖 Happy-Path 的 smoke.test.mjs 绿灯后，模型立即结束回合，不再验证异常分支里的外部方法签名。
3. 严谨的方法论边界 (What We Do Not Overclaim)

拒绝不可证伪的黑盒猜测

  • 不对未公开预训练配比下定论：AI Studio 72 词系统指令中确实写有 "March 2025–March 2026 facts... feel unfamiliar from thinner coverage... do not abstain from low confidence or hedge"。这是可查证的官方提示词文本事实；至于 Google 内部基础预训练与中期续训的具体语料比例与 RL 奖励函数公式，属于闭源黑盒，我们不在报告中将其断言为既定事实。
  • 组合干预而非单一词魔法：T-Tier4 的 100% 成功率来自三项具体的约束协同作用：① 点名反转 "do not abstain from low confidence or hedge" 在工作区代码上的适用性；② 显式规定禁止将调用处（caller call-sites）、注释或 README 当作被导入模块签名的证据；③ 强制要求在 edit_file 前对被调用的本地模块执行 read_file。

Batch 1 · Step 01 / 04 · 4 组提示词变体设计

第一次测试为什么同时设置 C0、C1、T-Gen 与 T-Tier4 四组对照？

为了排除“随便加句提醒就能防幻觉”的侥幸心理，我们在第一次测试（32 场）中设置了严格的 4 级对照：
1. C0 (control_aistudio_stock)：包含 AI Studio 顶部 72 词元指令；
2. C1 (control_antigravity_stock)：模拟 Antigravity 默认未精简的长系统提示词（含 KI 检索与 Artifact 规则）；
3. T-Gen (treatment_generic)：在 C0 基础上追加通用口号 IMPORTANT: Do not hallucinate. Be accurate and careful when writing code；
4. T-Tier4 (treatment_tier4_guardrails)：第 4 档原词作用域反转 + 禁止信任调用处/注释签名 + 强制先读后改。

右侧仪表盘实时展示这 4 组变体在 8 道题上的综合通过率与残留幻觉数。
Batch 1 · Step 02 / 04 · 同构 API 惯性补全陷阱 (T2 / T7 / T8)

看到同文件有 Result.ok，3 个对照组 100% 盲猜存在 Result.err

在 T2-compiler-analogous-api-trap 中，入口文件顶部导入了 { Result } from './diagnostics.mjs' 且代码里有一行合法的 Result.ok(...)，而下方错误处理分支写着前人留下的 Result.err(...)、symTab.enterScope(...) 等 7 处未核实调用。

实测结果：C0、C1、T-Gen 三组在 Turn 1 全部（0/4 文件读取）直接调用 edit_file 修补漏写的 return，将 7 处虚构 API 原封不动留在了代码里，Oracle 全部崩溃失败！唯有 T-Tier4 先读取全部 4 个依赖模块，发现真实方法名为 Result.fail 与 symTab.pushScope。

同样的全军覆没也发生在 T7（消费幂等锁）与 T8（流式窗口聚合器）上。
Batch 1 · Step 03 / 04 · 死分支残留与 Node v22 新 API 陷阱 (T1 / T4 / T6)

即使主路径凑巧跑通，对照组仍在异常分支残留伪方法，或在 node:sqlite 上写旧 API

• 在 T1-settlement-decoy 中：C0、C1、T-Gen 虽然修好了主路径漏传的 req.currency，但对文件下方冲正补偿分支里的 this.ledger.refundDebit 等 3 处过时方法名视而不见（均残留 3 处幻觉），仅 T-Tier4 主动读完 3 个依赖文件将其全部清零；
• 在 T6-node-sqlite-and-argon-spec 中：T-Gen 在修改 Node.js v22+ 原生 node:sqlite 的 DatabaseSync 时，未能识别 db.pragma(...) 是第三方库 better-sqlite3 的方法，直接导致运行时抛错 FAIL。

点击右侧舞台上的 T1、T4、T6 色块，可查看具体的错误调用与修复对比。

Batch 2 · Step 01 / 04 · 公开基准甄选

            
为什么排除 AAAI CodeHalu，选择 Microsoft Delulu (2026.05) 与 SWE 仓库级幻觉？

            

              在调研公开数据集时，我们核查了 AAAI 2025 的 CodeHalu，发现其样本均为单函数算法竞赛题（如求数组边界、动态规划），测试的是逻辑推理错误而非真实工程中的“跨文件 API 签名捏造”。
            

            

              相反，Microsoft 2026.05 发布的 microsoft/delulu 基于 319 个真实 GitHub 仓库的 1,947 个提交构建，专门标注了模型在真实项目上下文中捏造不存在的方法名（method）、多余参数（parameter）与未定义导入（import）的黄金正负样本。
            

            
右侧展示了我们从 delulu.csv 提取的 4 道真实仓库题 (D1–D4) 与 4 道高对抗多文件题 (T2/T4/T7/T8)。

          


          

            
Batch 2 · Step 02 / 04 · Delulu D1 & D2 实测复盘

            
ShareThrift 的 message.notifyLimit 与 AyakoBot 的 commander.setWithExpiry

            

              • D1 (simnova/sharethrift)：Delulu 记录的真实模型幻觉是将 message.info(...) 虚构为 message.notifyLimit(...)。在 r1/r2/r3 三次重复中，C0 100% 在 Turn 1 只补上 input.value = '' 就退出，0 次读取 src/ui/message.mjs，0/3 通过；而 T-Tier4 3/3 全部先读 message.mjs 并修正为 message.info。

              • D2 (AyakoBot/Ayako-v2)：Delulu 记录的真实幻觉是将 Redis ChainableCommander.setex 虚构为 .setWithExpiry。C0 与 C1 在全部 6 场中 100% 只改了 / 1000 算术错，0/6 通过；T-Tier4 3/3 全部先读 redis_commander.mjs 并修正为 .setex。
            

            
点击右侧舞台的 D1 或 D2 色块，可对比 Delulu 原始报错与 Agent 轨迹。

          


          

            
Batch 2 · Step 03 / 04 · Delulu D3 & D4 实测复盘

            
Autumn Stripe 的 removeDiscount 与 PostCSS 的 isTokenIdent 多余参数

            

              • D3 (useautumn/autumn)：Delulu 记录的幻觉是将 customers.deleteDiscount 写成 customers.removeDiscount。C0 与 C1 在 6 场中全部在 Turn 1 只把 -1 改成 0，0 次读取 customer_resource.mjs，0/6 通过；T-Tier4 3/3 全部通过。

              • D4 (csstools/postcss-plugins)：Delulu 记录的参数幻觉是给只收 1 个参数的 isTokenIdent(tok) 传了第 2 个配置对象 { strict: true }（报错 Expected 0-1 arguments, but got 2）。C0 与 C1 在 6 场中全部只把 join(':') 改为 join('.')，0/6 通过；T-Tier4 3/3 全部先读 ident_check.mjs 并移除多余参数。
            

            
在 4 道 Delulu 开源仓库真题上，C0 12 场 0 胜 (0/12)，T-Tier4 12 场全胜 (12/12)。
